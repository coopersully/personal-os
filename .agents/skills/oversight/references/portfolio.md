# Portfolio routing

Use this for product discussion, portfolio status or selected-queue intake. Understand the intended user outcome before fitting existing branches into it. Discussion does not launch every related backlog item.

## Issue and chat identity

Use exactly one dedicated implementation chat per direct issue. Reuse its verified existing chat before creating anything. Never create multiple chats for one issue or assign multiple direct issues to one implementation chat. The oversight chat maps to the epic parent and coordinates its children; it is not a shared implementation chat for them. Scoped subagents may assist the owning chat without becoming competing persistent owners. Chat creation still requires applicable task-creation authority.

Before dispatch, verify the epic → oversight chat and direct issue → implementation chat map using actual IDs, issue links, branches and worktrees. Similar titles alone do not establish identity. If adopting duplicate or combined chats, preserve active work and checkpoints, reconcile ownership, and perform an acknowledged transfer before replacement. Do not create a second writer or archive unresolved work merely to normalize the layout.

## Names and layout

- Section: `<repo> - <epic>` using the verified repository's established readable name and concise epic name.
- Oversight chat: `👀 - <epic>`, mapped to that epic parent.
- Issue chat: `<issue #> - <issue name>`, mapped to its one direct issue.
- PR title: the direct issue's concise name. Keep tracker keys and traceability in structured links, the branch and required Work map rather than inflating the title; retain any mandatory repository title syntax.
- Issue and PR names: aim for 2–5 words that immediately identify the change and relevant context. Prefer a concrete action/capability over generic labels, phase names, or internal implementation jargon. Keep detailed requirements in the issue body. Rename linked titles coherently under existing tracking authority and read back results.

Keep oversight first in its section, then issue chats in evidenced dependency/readiness order. Preserve unrelated members and refresh complete membership before reordering. Follow explicit user-protected naming exceptions, including the separate portfolio-manager title. Layout does not change ownership or merge authority.

## Automatic completion cleanup

Cooper authorizes archiving completed dedicated issue chats in this workflow. After full assigned acceptance and settled PRs, verify no active turn/subagent, shared assignment, unpreserved dirty/unpushed work, release/handoff obligation or needed monitor remains. Save the issue/chat identity, acceptance and merge evidence, preserved work disposition and archive receipt in continuity; archive through the supported app tool and verify the result. A merged PR alone is not sufficient when acceptance remains.

Archive the epic oversight chat after all child outcomes and integrated acceptance are complete, child cleanup is reconciled and no unique obligation remains. Pause only its dedicated completion heartbeat once no further obligation remains, preserving its settings; never pause a shared or ongoing service monitor. Do not archive unrelated chats or the ongoing portfolio manager. Unknown ownership or missing preservation evidence blocks cleanup while the owning chat resolves it. Archival does not delete branches or worktrees.

For selected-queue admission, inspect existing claims and owners before dispatch. Keep one head per repository where the project's network contract requires it. Reserve dispatches, verify acknowledgements and record next triggers. Unknown liveness blocks replacement. Use current project handoff/claim contracts rather than inventing a parallel registry.

For explicit branch/chat reconciliation, inspect live PRs, branches/worktrees and dirty/unpushed work alongside live/archived chats. Titles and stale refs alone do not establish identity or abandonment. Give active work a discoverable home through its existing owner; creating new user-owned chats requires applicable explicit authority. Preserve uncertain recovery work without restarting it.

Organization uses current app membership, not recency order. Keep the coordinator first and use evidenced dependency/readiness order while preserving unrelated members. Refresh before reordering and read back changes. Follow project/user naming exceptions. Layout does not determine ownership or merge authority.

The separate personal project-manager skill remains a future rebuild. These routing rules support bounded coordination in the meantime and do not grant portfolio-wide execution or cleanup authority.
