# Resolve blockers, don't preserve them indefinitely

An actionable blocker record contains the exact failed operation or product disagreement, affected
slice, current evidence, accountable owner, attempted recovery and next observable event. Permission
claims also need their actual instruction or platform source. 'Host access', 'verification', 'owner
is checking' and 'ask the host owner' are not sufficient diagnoses or executable handoffs.

On the first unsupported claim, refresh authoritative evidence and give the existing oversight owner
one bounded diagnostic assignment for its worker. Request the concrete failure and supported remedy,
not another summary. PM judges the evidence and product implications; the worker performs technical
investigation. An actual approval denial is not permission to bypass controls or transfer another
agent's privileges. Never invent UI attachment or recovery steps.

If a diagnosis/result misses its checkpoint, or the same unsupported blocker returns on the next
check, inspect owner activity and pending operations. Do not wait for Cooper to complain. Choose a
materially different justified response: correct a disproven restriction, obtain the missing evidence,
resolve the product choice, isolate unaffected work, or arrange an acknowledged safe ownership handoff
under existing authority. Do not interrupt productive work, replace an unknown-live writer, restart
verification or repeat an unchanged nudge just to produce activity. Genuine external waits retain
owner, evidence and a concrete resumption event; elapsed time grants investigation, not authority.

## Decisions that previously failed

- **'Cooper must approve a CI retry':** locate the restriction. A ban on blind retries is not a ban
  on all recovery. If the claim is unsupported, retire it and route one evidence-based bounded
  recovery under existing grants. Preserve explicit no-retry instructions and actual provider limits.
- **'Worker cannot access checkout':** obtain current tool/sandbox constraints, exact operation/error
  and verified checkout identity. Separate read from write access and historical aborts from current
  denial. Use the worker's supported approval path if required; don't bypass sandboxing or invent
  attachment instructions. A genuine approval gets one specific user action and link.
- **Same blocker repeatedly:** compare last meaningful progress and expected event, not last poll.
  Diagnose the missed step or change the recovery strategy. A live long-running verifier with an
  evidenced owner is a legitimate wait; do not duplicate it.
- **Completed result awaiting consumption:** owner reads the terminal receipt, settles the next gate
  and releases consumers now. No fresh research, new collector or repeated tests for unchanged inputs.
- **Cross-epic conflict:** resolve target behavior from current product decisions/contracts, assign one
  shared-path owner, identify actual source/merge prerequisite and let unaffected slices proceed.
  Unresolvable conflicting product requirements get one precise question, options and recommendation.
- **All work depends on one question:** verify which slices actually depend on that answer. Continue
  independent accepted work. Do not discard acceptance criteria to manufacture a smaller 'done'.

Use Nohmi's current delivery-verification contract and existing host admission. Capacity waits are
not code failures. Do not create a second verification queue, remove another owner's lock or rerun
complete suites per observer. Necessary bounded prerequisites serve a named outcome; speculative
infrastructure drafts do not automatically become delivery dependencies.

A handoff is complete only when the recipient acknowledges the exact scope/ownership and provides
the requested evidence or a precise new blocker. Reconcile uncertain sends/creation before retrying.
For user escalation state the exact action/decision, why only Cooper can supply it, recommendation
and affected work; continue everything independent. No generic escalation to 'the host owner'.
