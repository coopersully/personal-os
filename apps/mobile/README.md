# nohmi mobile foundation

Expo SDK 58 supplies a React Native application with iOS and web targets. The native
shell uses authenticated API sessions, workspace-specific native tabs and Apple's Liquid Glass
on supported iOS versions. Tasks includes tasks, reminders, lists, projects (active, completed
and cancelled), filters, history, archive and trash. Finance includes Overview, Spending, Plan, Accounts and Assistant read workflows,
plus category/notes editing, category budget limits and conversation sending. Today combines live
Tasks and Finance reads with a time/weather hero and optional foreground location. Other workspace experiences
retain their existing preview boundaries. Full Finance web parity (creation, approvals, imports and automation configuration)
remains in progress.
The existing web and Tauri desktop UI remain separate consumers of shared domain/API contracts.

Sessions use SecureStore; domain reads stay in memory and writes require connectivity. Encrypted
offline caching and Universal Links are not implemented in this increment. Device notifications
schedule up to 50 future deadlines locally and reconcile while the app is active; web edits made
while it is closed are not pushed to the device. See the mobile frontend standards and native API
boundary documentation for the current scope.

Reicon PNGs are generated from the canonical web registry with
`pnpm --filter @personal-os/mobile icons`. Native tab selection and glass rendering use Apple
controls; the vertical workspace picker uses custom interaction logic over native glass.

## Development

From the repository root:

```sh
pnpm install --frozen-lockfile
pnpm --filter @personal-os/mobile start
pnpm --filter @personal-os/mobile web
pnpm --filter @personal-os/mobile typecheck
pnpm --filter @personal-os/mobile export
```

Native projects are generated by Expo Continuous Native Generation and ignored by Git.
Change `app.json` or a config plugin, not generated Xcode files. The build commands regenerate
native files and install pods before compiling. `expo prebuild` needs
CocoaPods installed for native dependency resolution. No EAS account is required for local builds.

```sh
pnpm --filter @personal-os/mobile native:generate
pnpm --filter @personal-os/mobile build:simulator
pnpm --filter @personal-os/mobile archive
```

The Release simulator build needs no signing identity. Archive uses Xcode automatic signing
for John Cooper (`7J7HDVDCKQ`), bundle ID `app.personal-os.mobile`, version `0.1.0`, build `8`.
Archive builds explicitly bind to `https://nohmi-api.coopersully.me`, reject development API
overrides and disable dotenv loading. Verify the signed archive against the committed source.
Increment `ios.buildNumber` before every new App Store Connect upload and regenerate native files.

## TestFlight

1. Accept any outstanding Apple Developer Program agreement in the developer account.
2. Sign into the authorized John Cooper team in Xcode. Obtain a valid Apple signing certificate
   and profile through automatic signing; keep private keys in Keychain.
3. Use the existing [nohmi app record](https://appstoreconnect.apple.com/apps/6831315999/distribution)
   (Apple ID `6831315999`, SKU `personal-os-mobile`). The bundle identifier is already registered.
4. Archive, then open `apps/mobile/build/nohmi.xcarchive` in Xcode Organizer and validate/distribute
   to App Store Connect. Alternatively export locally from `apps/mobile`:

   ```sh
   xcodebuild -exportArchive -archivePath build/nohmi.xcarchive \
     -exportOptionsPlist ExportOptions.plist -exportPath build/export -allowProvisioningUpdates
   ```

5. Confirm processing, export compliance and internal tester availability in App Store Connect.
   Install and launch from TestFlight on a physical iPhone. Compilation alone is not acceptance.

After reviewing the archive, `pnpm --filter @personal-os/mobile upload` explicitly uploads it
using Xcode’s authenticated account. This export is restricted to internal TestFlight testing.
Build commands never upload automatically, and there is no OTA update channel. The app uses standard platform HTTPS and SecureStore cryptography; reassess export compliance
when adding cryptographic capabilities. Native SDK privacy
manifests are generated during prebuild; reassess declared collection on every added SDK.

## External boundary

The release owner operates Xcode → Apple signing/provisioning → App Store Connect → TestFlight.
HTTPS access and an active team membership with current agreements are required. Credentials never
belong in the repository. Builds are local foreground operations; a failed archive or upload is
not a published build. Retry explicitly after diagnosing the Xcode/Apple error, preserving build
logs under ignored `build/`. Verify the uploaded build number before retrying an uncertain upload.
Apple processing and device installation remain external evidence gates. Green local exports can
still coexist with expired profiles, agreement blocks, unavailable app IDs or rejected uploads.

`native:generate` is deliberately not named `prebuild`: package managers execute `prebuild`
automatically before `build`, which would regenerate native files during a web export.

The app uses Expo’s required React 19.3 and TypeScript 6 locally. The existing web app retains
React 19.2 and TypeScript 5.9. Explicit test peers and the `reicon-react`/`vaul` type-peer
extensions keep those dependency graphs isolated. Recheck both apps when upgrading either.

## Native tabs and authentication (November 5, 2026)

On iOS, each workspace uses Expo Router `NativeTabs`, backed by the system tab bar.
UIKit owns its selection, drag interaction, glass material and animations. The web
preview uses the custom dock. Tabs show system-positioned text labels beneath the canonical outline/filled assets
and the shared workspace tint. Settings' agent page sits outside its native tab group.

The app now requires an existing nohmi account. Set `EXPO_PUBLIC_API_URL` to an API
origin before starting/building; the default is `https://nohmi-api.coopersully.me`,
the same hosted API as desktop. Non-loopback origins must use HTTPS. Passwords are
submitted only to the configured API and never stored. The shared API client uses
`POST /v1/auth/login`, `GET /v1/me`, `POST /v1/auth/logout`, and password recovery.
Native requests explicitly omit cookies and attach the API's `Session` credential.
Session tokens are stored only in SecureStore/Keychain, under an origin-specific,
versioned key with `WHEN_UNLOCKED_THIS_DEVICE_ONLY`. No user or domain data is cached.

Startup validates the stored token before revealing any signed-in screen. Resume
revalidates the session. A 401 clears identity and stored credentials; a network
failure preserves the credential for retry without treating it as successful restore.
Logout revokes the server session before reporting success. Failed revocation leaves
retry available. Authentication errors use Sonner Native toasts. Writes are not queued.
The web preview keeps tokens only in memory, so reloading requires sign-in, and its
origin must be allowed by the API's CORS configuration. Do not relax production CORS
or put human credentials in browser storage to make local previews work.

Expo export/typecheck and session lifecycle unit tests cover local correctness.
A real account sign-in, cold restart, foreground expiry and logout on a physical
phone remain release smoke checks. Domain screens still contain sample data or empty
shells: authentication does not imply live Mail/Tasks/Finance data integration.

The iOS workspace selector uses an Expo UI SwiftUI Menu with an inline Picker.
The system supplies its glass presentation, selection checkmark and dismissal; the
trigger retains the canonical workspace icon and selection retains haptic feedback.
Web keeps its existing custom workspace menu. This requires @expo/ui in native builds.

The latest workspace picker supersedes the system Menu above: it is a vertical
control rendered with SwiftUI glassEffect and a moving glass selection capsule.
The app owns drag routing and haptics; Apple supplies actual material and animation.
It opens below the search field, keeps icons aligned, and supports direct dragging
from the closed trigger as well as tap-open/tap-select. Bottom tabs remain NativeTabs.

## Native Settings candidate scope

The source includes account Profile (identity, planning timezone/hours, home place and workspace
setup choices), Security & Access (sessions, password reset, owner-gated invitations), Connections,
Activity Log, persisted shared appearance and installed version/build. Personal Goals & Motives
and morning/evening Ritual configuration/history are domain-owned children. Workspace and Agent
settings reuse authenticated typed APIs and existing permissions, revisions and Finance outcomes.
Field/action classification, including current gaps and shared preferences consumed by other
devices, is tracked in the COO-211 — Mobile Settings delivery record.

Google/X setup uses an explicitly confirmed browser handoff and authoritative status refresh;
iCloud uses a secure app-specific-password form. Texting enrollment requires current consent and
explicit verification; an interrupted pending challenge survives background/foreground within the
mounted form. No provider callback or raw phone/code persistence is added.
Notifications reuse existing on-device task/reminder scheduling separately from global/Finance
server text-message policy. Desktop widgets, wallpaper, pets, login lifecycle and desktop alert
preferences stay desktop-specific. Activity loads at most the latest 100 events and never invents
cursor pagination or exposes private audit payloads.

This section describes current source scope, not a shipped/TestFlight or production-provider
acceptance receipt. Focused tests, native simulator evidence, the frozen-candidate verifier,
protected delivery and an installable TestFlight build are separate gates. Settings source uses
partial/revisioned saves, retained-draft recovery and Sonner feedback as specified by
`docs/design/mobile-forms.md` and `docs/design/feedback.md`.


The approved Settings refinement source adds canonical native provider artwork and provider-first
connection setup; focused Security/Agents/policy detail trees; shared personal editors with bounded
day sheets; grouped workspace preferences and accepted-write cache publication. Human session
listing adds server-derived `isCurrent`; an older API omitting it remains compatible and receives no
inferred current-device badge. Native-stack status-bar ownership requires the generated iOS
controller-based flag. Routine pull refresh uses a spinner and Sonner errors without success toasts.
These are source contracts; installable build and production acceptance require separate receipts.

## Native Finance push candidate

Finance notifications have a separate, explicit per-account opt-in in Settings → Notifications.
iOS permission alone does not opt in. The native adapter uses Apple's APNs device token from
`getDevicePushTokenAsync`, never an Expo push token or Expo delivery service. It re-registers on
foreground and token rotation, unregisters when permissions are revoked or consent is disabled,
and fences asynchronous results by the human-session epoch. Successful background synchronization stays silent; failures use a deduplicated Sonner error.
Explicit changes update one Sonner toast. Existing local Task due scheduling
and server text-message preferences retain their separate controls and lifecycles.

`PERSONAL_OS_APNS_ENVIRONMENT=sandbox|production` is trusted native build configuration;
`app.config.ts` embeds it in Expo extra and the APNs entitlement. A missing value disables the
Finance toggle. The archive environment explicitly sets `production`, independently of `__DEV__`.
After changing this value, regenerate/rebuild native code; changing JS alone cannot change the
signed entitlement or provisioning profile. The APNs key, Apple App ID capability, signing profile,
and backend environment/topic must agree. Device tokens remain private authenticated API inputs.

Payload data is limited to `{version: 1, kind: "finance", eventId, audience}`. Taps require a
matching current registration audience and an authenticated event lookup bound to this installation
before opening Conversation or Activity in the existing Finance assistant. Attention updates open
an authenticated native detail that rereads the current source summary/status and offers its
server-generated existing web review destination plus Finance chat. It does not introduce native
approval controls. Resolved or replaced notifications explain that the update is unavailable.
Web handoff revalidates the source and only permits the configured `EXPO_PUBLIC_APP_URL` origin
and supported Finance paths. Archive builds bind that origin to production; synthetic QA must set
it to the synthetic API's configured app origin. Payloads never carry money, transcript text, an
owner ID or a raw account/session token. Logout/account replacement removes response and token
listeners, invalidates outstanding callbacks and clears presented Finance notifications; the server
revokes session-bound registrations on logout. Previously delivered OS banners may already have
been visible; the app cannot retract information the OS already presented.

Provider acceptance, APNs delivery and physical-device presentation remain separate evidence.
Unit and mounted tests establish callback isolation, opt-in, routing and toast delivery. Simulated
notification injection establishes routing only. A signed production build on a physical device
is required to establish the actual production APNs registration/delivery path. Native permission
requests can await human action; device token acquisition has a 15-second deadline; network and native token failures keep opt-in unsuccessful and
are retried by explicit action or subsequent foreground synchronization for saved consent.
