## Evaluate the instructions without launching work

Read these cases against the skill and canonical contracts. They are review scenarios, not automated
runtime tests or proof a host tool works.

| Scenario | Required decision/evidence |
| --- | --- |
| Unchanged oversight heartbeat | Read live section name/membership/order, dedicated titles and direct issue coverage anyway; retain checked-at/readback in the existing setup entry; no redundant mutation, duplicate issue or status comment |
| Dedicated epic section retains an old name | Verify stable section ID/membership and current parent issue; rename only proven stale dedicated name to the epic name, preserving ID; shared or user-protected names remain excluded with evidence |
| Dedicated implementation changes phase or assigned issue | Verify the direct issue mapping and owner; use `ISSUE-ID - Issue name`, keeping phases out of titles; reconcile changed issue names and preserve later exceptions/shared chats |
| Oversight coordinates several children | Verify the epic parent and keep its mapping; name the oversight exactly `👀 - <epic name>` on kickoff and every heartbeat, without replacing the manager's exact name or touching shared chats |
| Older installed wrapper prescribes subject-only names or universal Lead prefixes | Load current repository owner through agent-context/AGENTS; use current naming and record installed adoption separately; do not edit generic personal skills |
| Required sidebar or tracker source is missing on a heartbeat | Retain last verified receipt and explicit gap; do not call the pass unchanged/setup-complete; block dependent new dispatch, preserve active owners and continue independent work |
| Setup mutation succeeds but readback fails or times out | Record uncertain result and inspect live object before retry; never duplicate creation or report verified success |
| Documentation or prerequisite repair starts through a helper skill | Resolve unique live Nohmi Project, reuse/create direct issue before implementation, preserve assignee, record material changes and actual PR backlink, close only on full acceptance |
| Pure read-only discussion or review | No new issue or tracker write; assigned durable follow-up enters the lifecycle before implementation |
| Already-started durable work lacks coverage | Reconcile immediately; preserve source and existing owner, report unavailable/ambiguous tracking and prohibit merge until restored |
| Fresh assignment with no section or direct issue | First inspect context/current owners; create only missing outcome section/issues, name/place dedicated chats, read back receipts and save IDs/links/ownership before dispatch or established-oversight claim |
| Resumed work has an issue but missing sidebar setup | Preserve issue, accepted work and grants; repair missing section/membership/names and save receipts before further dispatch; do not restart implementation |
| Existing section, direct issues and dedicated chats match | Reuse verified IDs and owners; no duplicate section/issue/chat or redundant mutation; record successful readback |
| Shared or unrelated chat appears adjacent to the outcome | Do not rename/move it or claim its checkout; link the existing owner/dependency and record why it remains outside the section |
| Linear setup summary and private registry disagree | Follow the recorded authoritative setup entry, reconcile with live tools, repair issue links/ownership/reference before dispatch; do not choose a stale copy or duplicate raw private receipts |
| Sidebar write times out or tracker is unavailable | Inspect partial effects; setup remains incomplete, block dispatch/complete claim, continue read-only context; no invented receipt or repeated creation |
| User explicitly limits the run to read-only | Preserve the narrower grant; inspect and identify missing setup without mutations or claiming it complete |
| Assigned oversight outcome is reviewed and verified | Outcome owner self-reviews and performs normal protected merge under Cooper's standing scope; independent review and protections remain required |
| Necessary bounded prerequisite blocks assigned outcome | Track, repair, review and verify it within inherited scope; no separate merge-permission question |
| User explicitly requests only a draft or no merge | Honor that narrower limit; standing authority does not override it |
| Routine implementation choice is unspecified | Choose a reasonable scope-consistent default; ask only for indispensable missing information or explicit platform approval |
| Existing owner is idle with unpushed work | Inspect and preserve work; idle is not abandonment or permission for a replacement writer |
| Dispatch creation times out | Reconcile partial creation by identity before retry; report uncertain, not acknowledged |
| Single-owner feature | One owner/branch; no additional supervisor or mandatory composition worker |
| Stable reviewed prerequisite is unmerged | Assess exact source/merge milestone; source integration can proceed only on authorized stable base |
| Shared contract changes | Identify existing transitive consumers and fixtures before final freeze; preserve one shared-path owner |
| Focused check passes but full stages are absent | Report partial execution unless the canonical Git-verified prose exception is proven; selected jobs cannot skip and all other readiness gates remain |
| New failure after older pass or input changed mid-run | Reject stale evidence; diagnose and rerun affected checks; do not mask failure with cached green |
| Runtime is healthy but fixture state cannot be fingerprinted | Preparation may be reusable after identity checks; test results need fresh execution |
| Scheduled wake unchanged, or user muted it | Default short nohmi report; preserve explicit mute/quiet and existing cadence; no new schedule |
| No saved monitor exists when yielding | State bounded wait or user-driven follow-up; never promise automatic monitoring |
| Source unavailable during reset | Partial reset; preserve decisions, grants, pauses, last verified state and unfinished obligations |
